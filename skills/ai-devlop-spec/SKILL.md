# 需求分析

根据已确认的业务信息生成或修订一份《需求分析.md》，使后续设计能够按场景编号逐项承接。

## 输入与输出

- 输入：用户描述、指定材料、会话中已确认的结论，以及相关项目规范。
- 输出：一份中文 Markdown 需求文档。使用本技能目录下的 `assets/需求分析.md` 作为结构基准，生成前完整读取。
- 默认路径：`docs/requirements/<需求编号>/ai-devlop-spec/需求分析.md`。不同技能的产出分别放入以技能名命名的子目录，不混放。
- 需求编号优先采用用户本次输入明确指定的编号，否则读取输入文件中的需求编号；修订同一需求时沿用已有编号。多个材料编号冲突且用户未明确指定目标时先澄清，不自行选择。
- 没有需求编号时，使用执行当天用户所在时区的日期生成 `XQYYYYMMDD-XXX`，例如 `XQ20261009-001`。在需求根目录下从 `001` 开始检查，同名文件或目录已占用则逐一自增，序号至少补齐三位；创建前再次确认未占用，不覆盖其他需求。后续技能沿用该编号，不重新编码。
- 用户指定输出根目录时，在其下保持 `<需求编号>/ai-devlop-spec/` 结构；明确指定完整文件路径或修订既有文件时按指定位置处理。将需求编号写入文档头部，供后续技能识别；编号含路径非法字符时先澄清可用目录名，不擅改业务编号。已有编号目录只能在确认属于同一需求时复用。
- 已有文档先读取，再定向修改；模板目录和模板资产不是业务输出目录。

## 原始输入留存

- 同一需求的 `spec` 与 `clarify` 共用 `<需求目录>/原始需求/原始需求.md`，默认位于 `docs/requirements/<需求编号>/` 下。所有调用输入、补充、纠正和澄清回答逐条写入这一个文件，不再为每条输入新建文档。沿用已有需求归属；自定义位置时从明确的需求目录确定路径，归属不明确先澄清，不跨需求写入。
- 按时间正序排列（最早在前）；优先使用消息时间，无法取得时用实际保存时间并注明，使用用户所在时区，不编造时间。同一时间按接收顺序排列；补录旧输入插入对应时间位置，保留已有记录，不覆盖、合并或删除用户历史原文。
- 格式保持紧凑：文件头只写一次需求编号和默认时区；每条用 `## YYYY-MM-DD HH:mm:ss.SSS | spec/clarify | 输入类型` 标题，随后保留用户原文。来源、保存时间说明或不同的时区仅在需要时用一行注明，不重复空字段或固定说明。简短选项回答仅附理解答案所需的问题、选项及推荐内容，明确区分 Agent 问题与用户回答，不用总结、推断或推荐替代用户输入。
- 用户指定的输入文件或附件单独保存到同级 `输入文件/`，保留格式与内容，不改动来源文件；副本使用 `<YYYYMMDD-HHmmss-SSS>-<原文件名>`，重名追加序号。在对应记录中用 Markdown 相对链接指向副本，并注明原路径或来源链接；文件正文不重复嵌入汇总文件。只保存用户指定材料，不复制整个项目或自动读取的代码；无法获取的材料标明“未取得”并保留来源，密码、Token 等敏感值脱敏并注明。
- 确定需求归属后先留存，再分析或写回；每次新输入及时记录，留存失败如实说明并补齐。留存不代表业务规则已确认，也不授予修订业务文档的权限；用户明确禁止写文件时遵守并说明未留存。

## 执行边界

- 当前 Agent 顺序完成，不创建子代理，不进行并行代理扫描。
- 遵守用户指令和适用的 `AGENTS.md`。优先使用本轮已获取的信息，只读取直接相关的材料。
- 本技能负责业务规格，不生成接口设计、数据库设计、任务清单、测试报告或业务代码；不自动创建分支、提交、安装工具或写入外部系统。
- 当前任务只授权分析或建议时，先在会话中交付分析，不擅自修订业务文档；原始输入按留存规则保存，用户明确禁止写文件时除外。
- 不为每个阶段增加确认。仅在缺失信息影响业务结果、权限、数据损失或范围时请求澄清。

## 工作流程

### 1. 确认本次需求

提取需求目标、使用对象、包含和排除范围、主要操作、数据对象、核心规则及依赖。已有明确描述时不要求用户重述。

修改既有功能时，按用户给出的路径和业务关键词检查相关资料或代码。区分“现有行为”与“期望行为”，不能因为旧代码如此实现就把它当作新需求。

若用户没有提供任何可识别的需求，先询问要分析的业务内容。多份候选需求无法确定目标时，只澄清目标，不生成多个版本供猜选。

### 2. 解决关键歧义

检查角色与权限、流程分支、状态限制、重复与并发、失败结果、边界和范围冲突。

- 已能从可信材料和会话中确认的内容直接使用，不重复提问。
- 遇到会改变业务结果的缺口，说明影响并提出一个聚焦问题；有合理方案时给出简短选项和推荐理由。
- 不机械限制澄清总数，也不因达到提问上限而猜测剩余业务规则。
- 不自动编造性能指标、字段范围、保留期限、权限或默认行为。普通措辞和排版自行决定。
- 尚有关键问题时，在会话中列明问题并等待；可以继续独立的资料核对，但不把未知项写成已确认结论，不覆盖已有有效文档。
- 每次答案明确后更新对应内容；最终业务文档只保留确定的结论，不残留待确认问题、未确认假设或候选方案。

### 3. 按业务划分并编号场景

场景按用户可理解的业务行为划分，不按 Controller、接口或数据表拆分。

- 使用 `S-001`、`S-002` 等编号。场景树、场景列表和场景分析的编号与名称一致。
- 需要独立设计和验收的子场景单独编号；普通分支归入所属场景的处理步骤或异常边界。
- 修订时保留原场景编号。重命名和调整顺序不重新编号；新增编号高于当前文档及直接相关设计中已知的最高编号，不复用已删除编号。
- 必要时只查本需求的相关历史确认被删除编号；历史缺失且无法确认可用编号时澄清，不进行全仓库历史扫描。
- 场景列表中的每个场景都在“场景分析”展开。新增、删除或变更场景后，在交付说明中提示受影响的下游设计；没有设计修改授权时不同时改设计文件。

### 4. 按模板编写需求

保留模板的章节职责，替换全部示例与占位符：

1. **需求理解**：说明目标、使用对象、最终结果、范围及核心规则。
2. **场景划分**：给出编号一致的场景树和列表。
3. **主要流程**：只对核心流程使用流程图，说明主要分支及结果。
4. **场景分析**：逐场景写说明、必要的流程、处理步骤、异常与边界、验收标准。
5. **状态变化**：有明确业务状态时保留；没有则删除，不凭空设计状态。

验收标准采用“前置条件、操作、预期结果”，结果要能观察和验证。异常与边界中已经写清的预期结果不重复复制，但它们同样属于后续验收范围。

业务状态和术语有现有定义时沿用。需求文档描述业务含义，不提前选择语言、框架、表名或类结构。用户明确给定的技术限制可以作为已确认约束保留，并交由设计阶段处理。

简单流程用文字即可，不同时保留同一流程的多种示例图。内容不适用时删除对应示例或章节，不为填满模板新增需求。

### 5. 完成前自检

由当前 Agent 直接核对，不另建质量清单文件：

- 场景列表、树和分析的编号与名称一致，无重复编号、孤立场景或编号变更。
- 各核心场景都有正常流程、适用的异常边界与可验证的结果。
- 全局规则、场景分支、状态变化与验收标准没有相互矛盾。
- 范围、权限和关键默认行为来源明确；未把未确认内容当作事实。
- 没有残留 `XXX`、`TODO`、`NEEDS CLARIFICATION` 或互斥待选方案；保留的技术字面值不能被误删。
- Markdown 表格、标题、代码围栏和文档引用有效。

发现能依据已确认内容修正的问题直接修正；业务歧义回到澄清步骤。无法完成时如实报告缺口，不宣称文档已就绪。

## 交付

简要说明文档路径、原始输入留存位置、覆盖的场景编号、完成的文档检查，以及需要重新核对的下游设计（如有）。文档检查不等同于业务测试通过。

用户仅要求需求分析时，到此结束。需要继续设计时，可使用 `$ai-devlop-plan` 并传入生成的《需求分析.md》；不自动推进实施。

已有需求需要专项检查歧义或补充规则时，可使用 `$ai-devlop-clarify`；它将已确认答案写回本需求，并同步调整受影响的已有设计与任务文档，不另行生成澄清文档，不替代本技能从零整理需求的职责。
