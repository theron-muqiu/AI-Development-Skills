# 需求澄清

对已有需求做有针对性的歧义检查，优先解决会改变业务行为、权限、数据结果和验收标准的问题。参考 Spec Kit clarify 的分类检查、顺序提问和逐答案写回，不依赖 `.specify/` 或扩展钩子。

## 输入与输出

- 必要输入：本次已有《需求分析.md》或等价需求材料，以及用户补充说明与适用项目规范。定位顺序为用户指定文件 → 当前会话明确生成或修订的需求 → 已明确需求编号目录中的需求。多个候选无法确定时询问目标，不按修改时间盲选。
- 没有需求材料时先说明所需输入；需要从零整理需求时建议使用 `$ai-devlop-spec`，不在本技能中擅自新建需求。
- 输出：直接修订原有需求及受影响的已有文档，包括《详细设计.md》《接口设计.md》《数据结构设计.md》和已有任务清单；不生成澄清记录、独立报告、新业务文档副本或 `ai-devlop-clarify/` 产出目录；用户原始输入按下述规则留存到共用的 `原始需求/`。
- 通过需求内已有链接、当前会话和明确的需求目录定位相关文档，核对需求编号与场景归属。不同需求或多个候选无法确定时先澄清，不跨需求改写。
- 沿用已有需求编号、文件位置和文档结构；本技能不为澄清重新编码或搬迁文件。已有材料没有需求编号但目标明确时仍在原位置修订，不为编号缺失创建新目录。
- 初次读取时核对原文已有结论，避免重复提问。没有重要歧义且没有新确认规则时直接交付检查结论，不为了产生修改重写文档。

## 原始输入留存

- 每次调用本技能时留存本次用户输入；后续补充、纠正和澄清回答也逐条留存。记录用户原文，不用需求总结替代，不把 Agent 推断或推荐当作用户输入。
- 同一需求的 `spec` 与 `clarify` 共用 `<需求目录>/原始需求/`，默认是 `docs/requirements/<需求编号>/原始需求/`。沿用已有需求归属与编号，不因再次调用创建另一套目录。自定义文件位置时从明确的需求目录确定留存位置；归属不明确先澄清，不跨需求写入。
- 以实际收到或保存时间命名，每条输入生成 `YYYYMMDD-HHmmss-SSS-<spec或clarify>.md`，例如 `20261009-143025-123-spec.md`。使用用户所在时区，文件内标明时间、时区、调用技能、输入类型及来源。已知消息时间优先使用；拿不到时记录实际保存时间并注明，不编造时间。文件同名则追加 `-001` 等序号，不覆盖历史输入。
- 正文按原文保留本次输入；用户只回答字母或“推荐”时，同时保留对应问题、选项和推荐内容作为上下文，并明确区分 Agent 问题与用户回答，保证日后能还原含义。
- 输入包含指定文件或附件时，记录原文件名、路径或链接，并在本条输入对应的 `<时间戳>-<技能>-附件/` 内保存可读取的原始材料副本，保留格式与内容，不修改来源文件；重名副本追加序号。只留存用户指定材料，不复制整个项目、无关目录或自动读取的代码。无法获取的远程内容、附件如实标明未取得，不伪称已备份；用户输入或材料中的密码、Token 等敏感值脱敏并注明脱敏位置。
- 先确定需求归属并留存已收到输入，再分析或写回文档；后续每次新输入收到后及时留存，即使最终未形成确认规则也保留原文。留存失败时如实说明并补齐，不把未保存说成已保存。
- 输入留存与业务文档分开：留存未确认回答不等于业务规则已确认，未确认结论仍不得写入需求或设计。普通检查、建议调用也留存输入，但不因此取得修订业务文档的授权；用户明确要求不写任何文件时遵守并说明本次未留存。

## 执行边界

- 当前 Agent 顺序完成，不创建子代理或并行代理扫描。只读取本需求相关材料，复用已获得的信息。
- 用户只要求检查或建议时只读交付，不修订业务文档；原始输入仍按留存规则保存，用户明确禁止写文件时除外。用户已经提供明确补充规则时直接整合，不要求再确认同一结论。
- 调用本技能要求澄清并调整文档时，同步修订受影响的原需求、已有设计和任务文档属于本次范围，不逐文档再次请求授权。用户明确只允许调整指定文件时遵守限制，并指出其他文档尚未同步。不得新建缺失设计或任务文档，不编写业务代码、不执行任务、不提交或发布。
- 不自动创建质量清单，不替审核者勾选现有清单。项目存在明确审核规则时遵守，普通待办不额外引入审批流程。
- 不自动追加 Spec Kit 的 Clarifications 章节；已确认业务规则放入需求对应章节，剩余问题只在会话中说明，不另建澄清报告；用户回答及理解回答所需的问题上下文按原始输入规则留存。未回答的问题、未确认假设和互斥候选不作为确定规则写入需求正文。

## 工作流程

### 1. 读取并检查需求

完整读取目标需求，并读取已明确归属于本需求的相关设计和任务中受影响的内容。必要时读取直接相关的现有设计或代码以核对事实，区分现有实现与期望行为，不把旧实现直接当作新需求。

按适用维度内部检查“已明确／部分明确／缺失／不涉及”：

- 目标、使用对象、包含和排除范围、角色权限。
- 核心流程、分支、交互结果、空数据与失败结果。
- 业务对象、标识唯一性、状态变化和生命周期。
- 重复请求、并发、冲突、部分失败与恢复行为。
- 外部依赖、输入输出约定、不可用时的业务结果。
- 已给定的性能、容量、安全及隐私要求是否可验证。
- 术语一致性、全局规则与场景规则冲突、异常边界、验收标准及占位内容。

维度不适用不算缺失。没有业务依据时不编造性能阈值、数据规模、保留期限或合规要求。普通措辞和排版自行修正，不机械询问；不把表名、字段类型、类结构等设计阶段选择当作业务澄清问题。

### 2. 选择高影响问题

优先处理影响范围、权限、数据损失、核心流程和验收结果的问题，其次处理其他会改变实现或验证方式的缺口。能从可信材料和用户已确认结论得到答案的直接使用。

每轮优先处理最多 5 个高影响问题，一次只问一个，不提前输出整列问题。这个上限用于控制单轮负担，不是完成标准：仍有关键缺口时明确记录其影响，在用户愿意继续时进入下一轮，不把达到数量上限当作需求已就绪。

提问前重新检查前一答案是否已经消除后续问题，移除重复或不再适用的问题。没有重要歧义时直接说明检查结论及下一步，不制造问题。

### 3. 逐项提问与确认

每个问题必须是用户可直接理解、可回答的完整问句，说明当前场景和具体选择；不能只写“权限规则”或编号当作问题。

- 先说明这个决定对业务结果、实现或验收的影响。
- 有合理选项时提供 2–3 个相互区分的 A/B/C 选项，写明各自后果与推荐理由；复杂业务确需更多选项时再扩展，避免伪选项。
- 允许用户回答字母、“推荐”，或提供自己的方案，不强制五字限制，不把建议当作已确认规则。
- 没有合理离散选项时提出聚焦的开放问题；无依据的答案不作为推荐。
- 答案仍有歧义或与已有规则冲突时围绕同一问题补充确认，不推进依赖它的问题；用户没有回复或超时不算接受推荐。
- 用户要求停止或稍后继续时立即停止提问，保留已确认成果，并明确尚未解决的关键问题。用户要求带缺口进入下游时说明受影响内容，不能宣称已完成澄清。

建议问法：

> 用户取消未发货订单后，退款应立即发起，还是审核通过后发起？
> 这个决定会影响订单状态变化和退款失败后的处理。
> 推荐 A：立即发起，符合目前已确认的自动取消流程。
> A. 取消成功后立即发起退款。
> B. 取消后进入审核，审核通过再退款。
> 也可以提出其他规则。

示例中的推荐必须有当前需求依据，不能在真实需求中照搬。

### 4. 每次确认后立即写回

得到明确答案后立即更新需求的相关章节，同时同步已有文档中受影响的位置并保存，再提下一问题，避免只将答案留在会话中：

- 范围、对象和全局规则写入需求理解；流程判断写入主要流程或场景处理步骤。
- 权限、失败与边界写入对应场景；状态规则同步状态变化；验收结果同步可观察的验收标准。
- 用确认后的规则替换过时或冲突表述，不重复追加两套规则。只改受影响位置，保留原章节顺序与稳定场景编号。
- 新增场景沿用 `$ai-devlop-spec` 的编号规则，高于需求及直接相关设计中已知最高编号，不复用删除编号。不为一句澄清重排全部场景。
- 同步《详细设计.md》的场景对应表、实现步骤、业务判断、异常与事务策略，以及《接口设计.md》的参数约束、权限、错误行为和示例、《数据结构设计.md》的字段约束、状态和关联规则。只修改确实受影响内容，不为澄清重做全部设计。
- 同步已有任务清单的场景覆盖、范围、依赖和完成标准，保留稳定任务编号；已完成任务因规则变化需要返工时明确重新打开并说明原因，不把文档调整当作实现已完成。
- 已有实现记录与新规则不一致时，仅如实说明关联任务需要返工或重新验证，保留历史验证事实，不伪造新结果。代码与新规则的差异在会话中说明，本技能不实施代码。
- 答案足以确定的关联文档改动直接完成；关联设计仍需关键决策时继续聚焦澄清，不猜测后写入。未解决期间明确指出文档尚未完全一致。
- 保存前确认文件没有被其他工作改动；有变化时读取最新版本合并本次定向修改，保护既有内容。本条结论涉及的全部文档保存成功后才说明已同步；写入失败时如实报告并补齐，不虚构完成状态。

尚未回答的内容仅在会话中维护，不作为已确认结论写入需求正文。用户已有需求中的未决描述不通过猜测替换；存在它们时不得宣称文档已就绪。

### 5. 核对跨文档一致性

每次写回后检查需求与相关设计、任务中的规则一致，没有旧表述残留冲突。核对场景编号与名称、接口字段与示例、状态编码、权限、异常处理、数据约束、事务策略、任务范围和验收标准的对应关系；验证相对链接与章节引用有效，保护不受影响的章节。

已经生成的文档不是只提示“需要更新”：在本次授权范围内直接同步确实受影响的位置。没有生成的文档不补建，无变化的文档不重写。仅影响技术设计的已确认约束写入对应设计位置，不把表名、类结构等实现细节塞进业务需求。

必要设计决定尚未明确、部分文件写入失败或用户限定修改范围时，在会话中准确列出尚未同步的文件、章节与影响，不宣称上下文已统一。已有任务和实现记录的状态必须真实，澄清检查不等同于代码测试或业务验收。

用“已解决／已明确／留待设计／未解决／不涉及”概括适用维度。可留待设计的内容必须确实不影响需求业务语义；未解决的关键业务问题不能归入“留待设计”来绕过。

## 交付

在会话中给出实际修改的原文档链接、已回答问题数量、修改章节、受影响场景和任务、剩余关键问题，以及跨文档一致性结论，不生成独立澄清交付文件，同时给出原始输入留存位置及未取得的材料（如有）。只有关键歧义全部解决、确认答案写回成功且受影响文档均同步时，说明本次澄清完成；否则明确部分完成与具体缺口。

需求已明确但尚无设计时，可建议使用 `$ai-devlop-plan`；已有代码需按新规则返工时说明相关任务与下一步，不自动调用其他技能或实施代码。
