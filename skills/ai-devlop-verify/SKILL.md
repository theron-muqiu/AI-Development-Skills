# 实现验证

在实现后独立核对真实实现与本需求依据，识别实现偏差、遗漏、风险和验证缺口。静态代码存在不等于运行通过，测试成功不等于需求完整，任务全勾选或实现记录声明不等于验收通过。

## 输入与输出

- 先定位当前项目根目录，结合用户指定路径、项目指令、仓库边界与来源归属确认；多项目或多需求无法唯一定位时先询问，不按当前目录或最新修改时间盲选。
- 定位顺序：用户指定材料 → 当前会话已明确的本需求材料 → 已确认需求编号目录。完整读取原始输入与已确认澄清、`需求分析.md`及验收标准、全部已有设计（包括`详细设计.md`、`接口设计.md`、`数据结构设计.md`）、`任务清单.md`、`实现记录.md`和适用 `AGENTS.md`、项目规范，沿明确引用读取相关约束，不以摘要或截断片段代替原文。
- 沿需求与任务定位并读取真实相关代码、配置、契约、数据定义和测试；必要时跨模块追踪，不局限于改动文件或记录所列文件，也不无目的扫描全仓。记录缺失或不可访问来源与影响，未找到不等于不存在。
- 保留需求、场景、验收、任务和 Rule ID；没有编号时用实际章节/代码位置，不擅造业务编号。需求编号缺失或冲突无法确认时先澄清，不生成新编号绕过。
- 默认报告：`ai-dev-docs/requirements/<需求编号>/ai-devlop-verify/实现验证.md`；用户指定输出根目录时保留 `<需求编号>/ai-devlop-verify/`，明确指定完整报告路径时按指定位置处理。确认同一需求，不覆盖其他需求或其他技能报告。
- 生成前完整读取 `assets/实现验证.md`；已有报告先完整读取。以前的检查或验证报告是可选追踪输入，不替代独立核查；不能继承旧结论而跳过本轮证据。来源链接按实际位置填写，不生成缺失文件的虚假链接。

## 项目宪法约束

- 每次运行必须实际读取项目根目录 `.ai-dev/memory/constitution.md`（L1）及同目录 `engineering.md`、`architecture.md`、`security.md`（L2），不以模板、旧报告或会话摘要代替运行时读取。
- 使用已批准且适用的生效正文及有效例外，记录版本、批准依据、Rule ID、强度和适用范围。草案、待批准修订及例外申请不视为生效。例外核对审批、范围、期限、补偿措施与复审条件，过期或越界不得默认沿用。
- 有依据的法律、监管、不可豁免合同义务和外部强制安全要求优先，不得内部豁免。L1 明确强制要求高于 L2，L2 例外不能豁免 L1；不以 L1 宽泛原则机械否定有项目事实、专业依据或已批准决策支撑的 L2，先寻找能同时满足的合理解释。
- L1/L2 或 L2 之间不可调和时，报告具体条款、原因、影响和所需决策，等待用户决策，不择利、不自动修宪；用户决策也不能豁免外部不可豁免义务。继续不受冲突影响的核查。
- 文件缺失、批准状态不明或证据不足时将相应范围标“未验证”，说明影响，不假装通过、不自动建宪法，也不机械阻断所有验证或全部后续工作。

## 执行边界

- 当前 Agent 顺序执行，不创建子代理或并行代理扫描。
- 用户调用本技能要求验证，授权仅创建或更新本技能自身报告；仅问建议、咨询或验证方案时只在会话回答，不写文件。不得修订需求、设计、任务、实现记录、宪法、业务代码或测试，不勾选任务、不自动修复或调用后续技能。
- 验证调用可在用户授权范围内运行安全的本地已有测试和构建；用户禁止或限定的检查必须遵守。先读取命令、脚本、生命周期钩子和配置，确认无禁止副作用再执行；未知脚本或无法确认安全时不运行，报告未验证并请求必要授权。
- 禁止自动安装/下载依赖、更新快照或基准、执行破坏性命令、迁移、部署、外部系统及真实数据操作；依赖缺失或测试需要网络/外部服务时不能自动越界。不得为了通过而改断言、跳过失败、切换规则或修复代码。不自动新增测试。
- 本地测试构建的正常可再生缓存/产物仅在已确认安全且授权允许时产生，不视为代码修订授权；会改受保护文件、生成快照、连外部系统或副作用不明则不执行。除自身报告外不主动修改或清理文件；不提交、推送、创建分支。
- 保护已有未提交修改，区分现状、用户改动和测试产物，不回滚或覆盖。报告保存前检查并发变化，重读并定向合并；不能安全合并时报告冲突，保留用户备注。

## 工作流程

### 1. 建立独立验证基线

记录需求编号、范围、来源版本/读取时点、代码版本与工作区已有改动、输入缺口、授权和环境限制。区分已确认排除与未确认排除，后者不能缩小验证范围，保留在矩阵。设计缺失不自动失败：简单需求有充分已确认依据时说明；影响方案的缺口不得靠实现反推为已批准设计。

从需求与验收逐项建立检查项，再对照设计、任务和实现记录，不从“已完成”清单反向限定范围。缺失记录或任务时仍核查可查部分，但不宣称完整验证通过。

### 2. 追踪真实实现与风险

逐场景从实际入口沿调用链到业务逻辑、权限、持久化与外部边界，记录入口、关键分支、调用关系和可复查位置。不能仅凭符号存在、文件名、注释、模拟实现或记录声明判定实现。按实际适用性核查：

- 正常、异常、空值、边界值、状态转换、重复/并发/幂等、失败恢复与跨任务组合行为；是否遗漏分支或不可达。
- 分层和模块依赖、数据归属、事务与回滚、集成失败和兼容策略；实际调用是否绕过设计边界。
- 认证授权、对象与租户隔离、输入校验、敏感信息、日志与错误处理、注入及信任边界；不执行攻击性或外部探测，不复制秘密或个人数据进报告。
- 接口路由、方法、请求响应、字段、类型、必填、状态码、错误语义和调用方契约；数据结构、默认值、约束、映射、读写、迁移与兼容设计是否一致。只读审查迁移，不执行迁移。
- 任务完成标准与实现记录是否有真实证据，适用工程/架构/安全 Rule ID 及有效例外是否满足。代码现状不自动凌驾于已批准规则。

### 3. 核查测试与授权内执行

读取已有测试的实际断言、输入、覆盖分支、夹具与 mock，识别仅覆盖成功路径、过度模拟或未验证关键行为的缺口。对照需求验收和风险选择必要本地已有测试/构建，遵守项目强制检查与用户授权；无法安全执行时记录原因，不自动补依赖或测试。

执行时记录工作目录、完整命令、代码/环境基线、执行时点、退出码、结果摘要及实际覆盖。明确区分本轮实际运行、静态检查和历史记录；历史测试结果只作来源证据，不冒充本轮执行。测试失败不修复，记录具体输出和影响，可在安全授权内定向诊断，不通过反复改条件制造成功。

编译成功不代表业务验收通过，单元测试通过不代表真实集成、安全或数据行为通过。静态确认的实现项与运行未验证项分开记录；不得编造覆盖率、性能、安全或端到端结果。

### 4. 覆盖、问题与复跑

建立覆盖矩阵：原始输入/需求/场景/验收 → 设计 → 任务 → 实现记录 → 实际代码调用链 → 测试与运行证据 → Rule ID → 结论。包含异常、边界、非功能、跨任务场景和无实现承接项；反向列出无需求依据的实现。无 Rule ID 用实际条款定位，不能伪造编号；不适用需有项目依据。

状态统一为“通过 / 发现问题 / 未验证 / 不适用”，同时注明证据类型和验证层次。证据不足标未验证，不以测试通过覆盖未查需求，不能把静态符合写成运行通过；总体结论说明已查范围和剩余缺口。

问题用稳定 `VER-001` 等 ID，写明证据位置、复现条件或静态推导、预期/实际差异、场景/任务/Rule ID、影响和修复建议。严重度“阻断 / 严重 / 一般 / 建议”按实际风险说明理由，与 MUST/MUST NOT/SHOULD/MAY 强度分栏，MUST 不自动等于阻断。

复跑沿用同一问题 ID，不重排复用，新问题追加新 ID。原报告问题逐项标“仍存在 / 已解决 / 未复核”；仅本轮独立证据证明消除才标已解决，未检查不得标解决，历史通过在条件变化后不能无依据沿用。

### 5. 保存与交付

仅保存本技能报告，给出报告链接、覆盖范围、状态分布、主要问题、实际执行命令结果和未验证项；分别说明静态结论与运行结论。存在遗漏、失败或未验证时不得宣称全部验收通过；建议后续修复及补充验证，但不改文档代码、不改任务状态、不自动修宪或部署。
