# 实现任务拆分

将已明确的需求与设计转化为可执行任务。参考 Spec Kit tasks 的业务场景组织、依赖排序和检查框格式，按实际规模划分一个或多个任务，不强制固定阶段或任务数量。

## 输入与输出

- 必要输入：本次《需求分析.md》或包含稳定场景编号的等价需求材料。读取已有《详细设计.md》《接口设计.md》《数据结构设计.md》和适用项目规范；只读取本需求相关文件。
- 定位顺序：用户指定材料 → 当前会话明确生成或修订的需求与设计 → 已明确需求编号目录中的材料。多个候选无法确定时询问目标，不按修改时间盲选。
- 技术设计缺失时，简单需求且实现位置、契约和数据影响均可从已确认材料或现有代码查明，可以直接拆分；缺失信息会改变实现方案时先说明所需设计，不在任务中猜测接口、字段或架构。缺少稳定场景编号时请用户授权通过 `$ai-devlop-spec` 补齐，不自行另造场景编号。
- 输出：使用 `assets/任务清单.md` 作为结构基准，生成前完整读取。默认路径为 `docs/requirements/<需求编号>/ai-devlop-task/任务清单.md`。输入在同一需求的 `ai-devlop-spec/` 或 `ai-devlop-plan/` 下时，使用其同级 `ai-devlop-task/`。
- 需求编号优先采用用户本次输入明确指定的编号，否则读取输入文件中的编号；同一需求沿用已有编号，也可从明确的需求编号目录确认。材料编号冲突且用户未明确指定目标时先澄清。
- 无编号时，按执行当天用户所在时区的日期生成 `XQYYYYMMDD-XXX`，在需求根目录下从 `001` 开始检查同名文件或目录，已占用则自增，序号至少补齐三位；创建前再次检查，不覆盖其他需求。将编号写入任务文档头部，不擅改输入文件。
- 用户指定输出根目录时，保留 `<需求编号>/ai-devlop-task/` 结构；明确指定完整文件路径或修订既有文件时按指定位置处理。编号含路径非法字符时先澄清可用目录名，不擅改业务编号；已有编号目录仅在确认属于同一需求时复用。
- 已有任务清单先读取再定向修订。按实际位置设置来源链接，默认使用 `../ai-devlop-spec/需求分析.md` 和 `../ai-devlop-plan/详细设计.md` 等；缺失文件不保留虚假链接。

## 执行边界

- 当前 Agent 顺序完成，不创建子代理，不进行并行代理扫描，也不为任务生成代理分工或并行执行指令。
- 遵守用户指令和适用的 `AGENTS.md`，复用已获取信息，不扫描无关模块。
- 本技能只拆分任务，不编写业务代码、执行任务、安装工具、运行迁移、提交、创建分支、部署或修改外部系统。
- 不自动创建独立研究报告、质量清单、测试报告或每任务一份文件；任务信息集中在《任务清单.md》。不擅改需求与设计。
- 用户仅要求建议时先在会话中交付。仅在缺口影响范围、业务结果或实现依赖时澄清，不逐任务要求确认。

## 工作流程

### 1. 确认实现范围与依据

读取需求目标、范围、场景编号、规则、异常边界和验收标准，结合设计中的场景对应表、实现入口、接口、数据、事务与兼容策略确认本次实现范围。

只检查必要的相关代码路径、构建配置和同类实现。区分已有能力与拟新增内容，不把设计描述当作代码已实现。需求和设计冲突、范围不明确或关键设计缺失时说明具体影响，等待澄清；可以继续无关缺口的资料核对，不覆盖有效清单。

### 2. 按可交付结果拆分任务

- 简单、内聚、可一次完成并验证的需求只生成一个任务。多个紧密关联场景可归入同一任务。
- 当存在独立可交付的业务结果、明确前置依赖、不同改动风险或过大实现范围时，拆成多个任务。优先按业务场景组织，不机械按 Controller、Service、DTO、数据库各拆一个任务。
- 每个任务说明目标、覆盖场景、包含与排除范围、实现步骤、涉及位置、前置依赖和完成标准，使执行者无需重新决定业务规则即可实施。
- 共用前置工作只有实际阻塞多个任务时才单独成任务；否则放入最早需要它的任务，避免重复实现。联调、迁移和兼容处理仅在实际需要时安排，不为模板补齐初始化、基础设施或收尾阶段。
- 沿用需求场景编号 `S-001` 等，任务可覆盖多个场景，场景也可分布于多个任务，但对应关系必须明确。跨任务场景说明组合后的验收方式，不宣称每个前置任务都能独立交付完整业务功能。
- 每个涉及的正常规则、异常边界、状态变化和验收标准都应有任务承接。不增加需求外功能，不自动定义 MVP、业务优先级、工期或负责人；已有明确优先级时沿用。

### 3. 编号与依赖排序

按前置依赖排序使用 `T001`、`T002` 等稳定任务编号。任务总览每条采用 `- [ ] T001 [S-001] 任务目标（实现位置）`；多场景用 `[S-001,S-002]`，共用前置任务用 `[基础]` 并在详情说明服务的场景。路径使用已核对的项目相对路径；拟新增路径明确标为“拟新增”，不能确定具体文件时写已核对模块目录与待落实的文件职责。

依赖引用任务编号，无依赖写“无”。任务不得自依赖或循环依赖；已有业务优先级在依赖允许时优先安排。默认由当前 Agent 顺序执行，不使用 `[P]` 并行标记。

修订清单保留已有任务编号与真实完成状态，不因重命名或排序重新编号。新增编号高于已知最高编号，不复用删除编号；删除任务说明原因及依赖调整。没有实施证据的新任务保持未完成，已完成任务需要返工时明确重新打开并说明原因，不把清单检查通过当作实现完成。

### 4. 编写任务详情与完成标准

完整读取模板并替换全部示例。每个总览任务都要有对应详情，步骤描述具体动作与结果，引用相关需求、设计章节或实现位置，避免只写“完成后端”“完成测试”等泛化指令。

完成标准承接需求验收结果和设计约束，写清如何验证以及可观察的预期结果。遵守项目既有验证范围；不机械为每个任务新增测试文件，不自动要求 TDD 或端到端测试。只有用户、需求或项目规范要求时，或关键风险确实需要时，安排独立测试任务；常规必要验证写在所属任务的完成标准中。生成清单阶段不执行验证，不填写虚构通过结果。

代码任务应承接项目方法抽取、注释、入口与关键业务节点日志规则，必要时在实现步骤或共用约束中说明，避免每个任务重复整段规范。

### 5. 完成前核对

由当前 Agent 直接检查，不生成额外检查文件：

- 至少一个任务，数量与范围相称；总览、详情的编号和名称一致，没有重复或孤立任务。
- 本次范围内每个场景及其异常、验收都有承接；范围外场景说明已确认依据，不自行排除。
- 任务范围不重复，共用工作有明确归属；任务有具体实现位置和可验证的完成标准。
- 所有依赖指向有效任务，没有环或缺失前置工作，执行顺序可行。
- 需求、设计与任务的接口、字段、状态、事务及兼容策略一致，没有未确认的实现决定。
- 需求编号一致，来源链接和章节引用有效，无未替换占位符；未把计划写成已完成工作。

能依据已确认信息修正的问题直接修正；关键缺口回到澄清，不以猜测补齐。

## 交付

给出清单链接、需求编号、任务数量、场景覆盖、依赖顺序及核对结论。说明这里只完成任务划分，未执行实现或业务验收。用户没有要求实施时，到此结束。

需要按清单完成全部任务时，可使用 `$ai-devlop-implement` 并传入本需求任务清单；不自动调用。
