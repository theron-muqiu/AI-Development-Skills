# 项目宪法（constitution）

根据项目实际情况创建或修订两级规范：L1 定义长期有效、跨专业共同遵守的根本原则，L2 分别定义工程、架构和安全要求。以项目事实、用户明确要求和本技能附带模板为依据，完成规范编写、版本维护与一致性检查。

## 固定产物与优先级

先确定项目根目录；多仓库或多个候选不能猜测，先询问。所有产物固定在该项目的 `.ai-dev/memory/`：

| 层级 | 文件 | 职责 |
| --- | --- | --- |
| L1 | `constitution.md` | 5–8 条长期、跨专业的根本原则及共同治理规则 |
| L2 | `engineering.md` | 工程实践和质量约束 |
| L2 | `architecture.md` | 基于本项目实际情况的结构、边界及演进约束 |
| L2 | `security.md` | 本项目适用的安全与信任边界约束 |

使用上述固定路径和文件名，不擅自改变目录、名称或职责。发现其他目录或重复宪法时，先核对权威来源，不自动搬迁、删除或合并，避免产生两套相互冲突的规范。

- 法律、监管、不可豁免的合同义务和外部强制安全要求优先于项目内部规范，不得通过内部审批豁免；适用性必须有依据，不凭空假定。
- L1 高于 L2；L2 是 L1 的专业化具体实现，不得放宽、规避或暗中取代 L1 的明确强制要求。
- 不得用 L1 的宽泛原则机械否定有明确项目事实、专业依据或已批准决策支撑的 L2 规则；优先寻找能够同时满足两者的合理解释。
- L2 之间发生冲突必须明确报告。无法协调时指出具体冲突条款、原因和影响；存在实质冲突则等待用户明确决策，不自行选择有利于当前实现的规则，不擅自修改已批准规则，也不将冲突版本标为生效。
- 实际代码只是现状证据，不自动凌驾于已批准规范；未确认建议不得冒充现行约束。用户决策仍受不可豁免的外部义务约束，修订须遵循审批机制。

## 执行边界

- 当前 Agent 顺序执行，先读后改。只读咨询、审查或建议仅在会话中交付；创建／修订请求才授权相应文件写入，且受用户指定范围限制。
- 只维护上述四份文件，不新增治理领域或独立文件，不生成草案副本、独立变更日志、质量清单或业务代码。
- 不提交、创建分支、部署、自动安装依赖或调用后续开发技能。不自动修改需求、设计、任务、模板、CI 或业务代码。
- 既有文件必须完整读取并定向修订，保留未受影响内容、历史日期、稳定条款编号和审批记录，不用模板覆盖现有内容。保存前复核文件是否变化；有并发修改时重读合并，不强行覆盖。
- 缺失文件只能在本次授权创建范围内新增。内部一致性检查不自动授权修改其他宪法文件；超出授权范围的冲突在会话中说明并等待决策。

## 工作流程

### 1. 读取现状与原文件

1. 读取项目指令、项目介绍及现有四文件；已存在者完整读取，缺失者明确记录。查找相关既有规范或架构决策，识别其适用范围和批准状态。
2. 有针对性地读取构建／依赖配置、目录与模块入口、测试和 CI 配置、相关接口及数据结构、安全配置；只查与拟定规则相关的内容，不无目的全仓扫描，不复制密钥或个人数据。
3. 整理“已查证现状（路径／章节）／用户已确认约束／拟议变更／未知项”。记录证据的局限：配置存在不等于 CI 已通过，现有实现不等于已批准政策，未找到不等于不存在。
4. 首次创建完整读取 `assets/constitution.md`、`assets/engineering.md`、`assets/architecture.md`、`assets/security.md`；修订时读取相关模板及治理结构。所有占位提示都待项目事实或明确决策替换，不是默认技术栈或已批准规则。

### 2. 澄清重大缺口

优先确认项目范围与根目录、现行规范权威性、目标与关键风险、重大架构约束、身份及数据边界、审批主体与版本策略。只问会显著改变规则的缺口，说明影响并给出有依据的选项；已有明确答案不重复提问。

- 不编造技术栈、模块、认证方式、合规义务、覆盖率、SLA、漏洞修复时限或审批人；建议值必须标为提案并取得确认。
- 绿地项目没有实现证据时，以用户确认的业务／技术约束提出候选架构，说明取舍，标明“拟议”；不能把单体、微服务、DDD、分层等通用模式直接写成项目事实。
- 重大缺口未解决时暂停依赖它的正式定稿。用户允许先出草案时，将未决项和影响明确列出；不把未回答、跳过或沉默当批准。

### 3. 分层起草

**L1**：定义项目长期有效、跨专业共同遵守的根本原则，建议保持 5–8 条。每条有稳定编号、明确义务、理由与决策判据；避免空泛口号。不包含具体技术栈、框架、工具、目录、编码风格、工具命令或实现细节，这些下放 L2。L1 负责共同治理原则、规则优先关系、审批和例外机制，治理内容不计入核心原则条数。

**L2**：保留各领域指定章节，基于真实项目制定明确可执行的要求，不把通用最佳实践直接认定为现行约束。每条规则统一采用以下字段：

| 字段 | 填写要求 |
| --- | --- |
| Rule ID | 唯一且稳定的编号；沿用已有编号，新编号在三份 L2 间不得重复，正式使用后不随意重编号 |
| Title | 规则名称 |
| Strength | MUST / MUST NOT / SHOULD / MAY，分别表示必须、禁止、建议、允许；SHOULD 写明偏离条件 |
| Scope | 适用范围 |
| Requirement | 明确、可执行的具体要求 |
| Rationale | 制定原因 |
| Evidence | 可追溯的项目事实、用户约束或批准决策依据 |
| Verification | 如何验证，不填写虚构执行结果 |
| L1 Reference | 对应 L1 原则编号，可引用多个；无直接对应时注明独立依据，不强行挂靠 |

未确认技术约束只能作为草案，不能写成已批准规则。不适用章节保留标题并说明项目依据，未知不能直接标记“不适用”。规则强度与违规严重程度不同，不混为一谈，不强制增加 P0、P1、P2 优先级字段。

- Engineering：Coding Standards / Code Quality / Testing / Dependency Management / Error Handling / Logging / Build / CI/CD / Documentation。
- Architecture：Architecture Style / Layer Boundary / Module Boundary / Dependency Rules / Data Ownership / API Contract / Transaction Boundary / Integration / Extensibility / Architecture Testing。必须使用核实的模块、职责、允许及禁止依赖、数据归属和实际接口／事务边界；无对应概念时说明原因。给出与项目规模、运行形态和约束的联系，不填通用模式清单。
- Security：Authentication / Authorization / Data Isolation / Sensitive Data / Input Validation / Secure Communication / Audit Logging / Dependency Security / Error Handling / Security Testing。按真实信任边界、数据类型和威胁制定；跨文件的错误处理、日志、依赖与测试职责互相引用，避免重复冲突。

### 4. 版本、日期与审批

四文件分别记录状态、版本、首次批准日期、最近修订日期、审批主体／依据；L2 另记录所依据的已批准 L1 版本。治理总规则在 L1，L2 引用它，不复制成四套流程。

- **首次版本**：无历史版本时提议草案 `0.1.0`，首次正式批准提议 `1.0.0`；先确认项目版本约定，不擅自认定已经批准。现有合法版本继续沿用，缺失或不合法的历史版本先澄清，不重置。
- **语义版本**：MAJOR 用于删除／重定义原则或不兼容约束变更（包括使既有合规实践不再合规的收紧）；MINOR 用于兼容新增原则、规则或实质扩展；PATCH 只用于不改变规范含义的澄清、措辞、排版与链接修正。综合变更取最高等级，明确旧版 → 拟议新版及理由。只有实际变化的文件才升级，不为保持版本一致而机械升级四文件；禁止把实质变更藏在 PATCH 中。
- **日期**：使用 `YYYY-MM-DD`。首次批准日期只来自确实发生的批准，未知写“待确认（历史缺失）”，未批准写“未批准”；首次创建草案不能冒充批准日期。最近修订日期取实际修订日，确认所用时区，不虚构历史日期。无实质文件变更不刷新版本或日期。
- **审批**：提出变更摘要、差异、理由、版本增量、影响和未决项，交由已确认的有权主体明确批准。普通写文件授权不等于批准内容；Agent 不自任审批人。记录可追溯的审批依据，不虚构身份、时间或会议。
- **保护生效版本**：新建时可以把经授权的草案写入固定文件并显著标注“草案，未生效”。已有已批准文件修订未获批准时，在原文件末尾的“待批准修订”节记录完整提案（如获授权），保留生效正文、版本和批准日期；不得用草案替换生效正文或另造文件。批准后才定向应用提案、更新版本和日期，将审批及变更摘要保留在原文件内。已批准版本仍有重大未决项时不得宣称生效。
- **例外**：记录 Rule ID、Exception Reason、Affected Scope、Risk Assessment、Compensating Measures、Approver、Approval Evidence、Expiration Date、Review Conditions，保留已有责任人、状态和退出条件。字段未确认的只是待批准申请。L2 例外不得豁免 L1；涉及 L1 约束变化必须先按其治理规则修宪。外部不可豁免义务不得通过内部审批或修宪绕过，过期例外不得默认续期。

### 5. 保存与最终核对

- 确认只写授权的四文件；链接使用同目录相对路径，编号稳定，模板占位符在已批准正文中全部消除，草案占位项集中列明。
- L1 建议保持 5–8 条核心原则，且无专业实现细节；三份 L2 指定章节完整，每条规则包含统一的九个字段，实际架构有事实或已确认目标支撑。
- 修改 L1 后检查三份 L2 与新原则是否冲突；修改 L2 后检查其是否违反 L1，并核对相关 L2 之间的冲突。按冲突处理规则解释与澄清，实质冲突未决时不修改已批准规则。
- 检查 Rule ID 是否重复、是否误改已有编号，以及 L1 Reference 和跨规则引用是否正确；独立依据明确说明，不伪造对应关系。
- 检查批准状态、语义版本、日期、依据 L1 版本、例外有效性与冲突处理一致；存在未决重大缺口不标已批准。
- 保存前及保存后均对照原文件复核，确认没有意外破坏其他有效规则、丢失历史批准信息或无关内容；检查实际保存内容与拟议／批准状态一致。只报告真实保存与内部检查结果，失败时指出哪些文件未成功。

## 交付

列出实际创建／修订文件、草案或已批准状态、各文件版本与增量理由、L1 原则摘要、关键 L2 决定、宪法内部一致性检查结论和剩余批准／澄清项。仅在全部检查且无未决项时声称完成相应阶段；不自动进入需求、设计、任务或实现。
