## 规则填写格式

以下专业章节中的每条规则均按此九字段格式填写，可按实际需要重复规则块；章节引导不是已批准规则。编号正式使用后不随意更改，新编号须在三份 L2 中唯一，不重排已有编号。Strength 是约束强度，不是违规严重程度，不强制增加 P0/P1/P2 字段。未知事项不能写成“不适用”；确不适用的章节保留标题并说明事实依据。

| 字段 | 内容 |
| --- | --- |
| Rule ID | [唯一、稳定的规则编号] |
| Title | [规则名称] |
| Strength | [MUST / MUST NOT / SHOULD / MAY；分别为必须、禁止、建议、允许，SHOULD 注明偏离条件] |
| Scope | [适用范围] |
| Requirement | [明确、可执行的具体要求] |
| Rationale | [制定原因] |
| Evidence | [项目事实路径／章节、用户约束或批准决策依据；不把通用最佳实践当现行约束] |
| Verification | [验证方法；不伪造执行结果] |
| L1 Reference | [一个或多个 L1 编号；无直接对应则说明独立依据，不强行挂靠] |

未确认技术约束只作为草案，不能写成已批准规则。依据和验证方式逐条填写，不用文档级来源替代。

## Authorization

## Data Isolation

[依据实际用户、组织、租户或环境边界规定数据访问隔离、后台任务和缓存／导出等适用路径；无多租户不能强行套租户模型，但仍评估已有信任边界，说明验证方式。]

## Sensitive Data

[识别真实敏感数据类别，规定必要的采集、最小使用、存储、传输、展示、保留与删除约束及密钥管理责任；具体期限和法规依据必须确认，例子仅用脱敏占位值。]

## Input Validation

[列明实际不可信入口、结构与业务校验责任、大小／类型等已确认限制和拒绝语义；按项目技术评估注入、路径、上传等风险，不无依据宣称所有风险均存在或已防护。]

## Secure Communication

[按实际网络／进程／外部集成边界说明通信保护、对端验证、证书或信任配置的管理责任；协议与算法须有事实或批准依据，不把本地工具假设成公网服务。]

## Audit Logging

[明确哪些安全相关行为必须可追溯、记录哪些最小身份／资源／结果信息、访问与防篡改要求，以及经确认的保留／删除规则；区分工程诊断日志，不记录秘密或不必要敏感载荷。]

## Dependency Security

[根据实际依赖与供应链说明来源可信度、漏洞发现与分级、评估修复、例外接受和验证责任；扫描工具和处理时限有依据才填写，依赖版本管理引用 engineering.md，不能以扫描配置存在冒称无漏洞。]

## Error Handling

## Security Testing

[将真实威胁和前述规则映射为身份／越权／隔离／输入／敏感数据／依赖等适用测试，说明范围、责任与验收依据；仅在授权环境安排主动测试，计划与已执行证据区分，不生成虚假通过结果。]

## 治理与例外

遵循 [L1 分层与适用规则](constitution.md#分层与适用规则)及[治理](constitution.md#治理)。L2 例外不得豁免 L1，外部不可豁免义务不得由内部审批豁免；实质冲突等待用户明确决策，不擅自修改已批准规则。版本、日期和审批按 L1 统一机制维护，仅实际变化的文件升版，不机械对齐版本。
