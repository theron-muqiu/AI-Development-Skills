# 按任务实现需求

以任务清单为执行依据，持续推进全部任务实现，直到所有完成标准满足或存在无法自行解决的明确阻塞。参考 Spec Kit implement 的前置检查、依赖执行、进度跟踪和最终验证，不依赖 `.specify/` 或其扩展钩子。

## 输入与输出

- 必要输入：本次《任务清单.md》及其引用的《需求分析.md》；读取已有《详细设计.md》《接口设计.md》《数据结构设计.md》、适用的 `AGENTS.md` 和相关项目规范。
- 定位顺序：用户指定任务文件 → 当前会话明确生成或修订的清单 → 已明确需求编号目录中的清单。多个候选无法确定目标时先澄清，不按修改时间盲选。
- 清单缺失或没有可执行任务时说明缺口，请用户授权通过 `$ai-devlop-task` 补齐；需求与设计的关键决定缺失或冲突时先澄清，不自行发明业务规则。简单需求没有独立设计文件，但任务中已有充分实现依据时可以实施。
- 主要产出：按任务修改项目规定位置的代码、配置及必要测试，并更新输入任务清单的检查框；技能文档单独落地为 `docs/requirements/<需求编号>/ai-devlop-implement/实现记录.md`。输入在本需求技能子目录下时使用同级 `ai-devlop-implement/`，不把业务代码放进文档目录。
- 需求编号优先使用用户本次输入明确指定的编号，否则读取输入文件中的编号或明确的需求编号目录；同一需求沿用已有编号。编号冲突且用户未明确目标时先澄清，不生成新编号来绕过冲突。
- 无编号时，按执行当天用户所在时区的日期生成 `XQYYYYMMDD-XXX`，在需求根目录从 `001` 开始检查同名文件或目录，已占用则自增，序号至少补齐三位；创建前再次检查，不覆盖其他需求。记录所选编号供后续沿用，不擅改需求或设计文件。
- 用户指定文档输出根目录时保留 `<需求编号>/ai-devlop-implement/` 结构；明确指定完整文件路径或修订既有记录时按指定位置处理。编号含路径非法字符时先澄清目录名，不擅改业务编号。已有需求目录仅在确认同一需求时复用。
- 完整读取 `assets/实现记录.md` 后按真实结果填写，已有记录先读取再修订。默认引用 `../ai-devlop-task/任务清单.md` 等，按实际位置调整，不保留不存在的文件链接。

## 执行边界

- 当前 Agent 顺序执行，不创建子代理，不进行并行代理扫描，不因任务带 `[P]` 标记而启动并行代理。
- 用户调用本技能要求实现时，代码修改、必要本地验证和任务状态更新属于本次授权，不逐任务请求确认。用户明确限定部分任务时以该范围为准，否则处理全部未完成任务。
- 遵守用户指令和项目规范，保护既有未提交改动，不回滚、删除或覆盖不属于本次工作的内容。不无目的扫描全仓库，不新增无关重构。
- 本地实现不自动授权提交、推送、合并、发布、部署、生产数据操作或发消息。需要这些动作时，先完成可审阅的本地成果，再依据用户已有授权处理；无授权时在交付中说明待执行动作。
- 不自动执行 Spec Kit 扩展钩子或未知脚本。使用项目已明确的构建和验证流程，不机械创建各类忽略文件，只在本次产物确有需要时补充适用规则。
- 不自动要求 TDD 或端到端测试；用户明确禁止的验证不得执行。项目已有强制检查必须完成，确实无法运行时如实记为受阻，不用勾选任务掩盖缺口。

## 工作流程

### 1. 核对前置条件与工作区

读取完整任务清单，提取任务编号、场景、实现范围、前置依赖、文件位置及完成标准，核对需求编号与来源。

- 检查编号重复、依赖缺失、自依赖和循环依赖，确认清单与需求、设计一致。能从已确认材料修正的普通路径或排序问题直接修正；改变需求范围、业务规则或核心技术方案的缺口先澄清。
- 了解当前工作区变更，只读取相关代码、构建配置、依赖与测试入口。区分用户已有改动与本轮改动，确认技术栈和项目分层，不把拟新增设计当作已有代码。
- 已有审核门禁按项目明确规则检查；审核清单不能当作实施完成证据，不替审核者勾选。普通未完成备注不自动引入额外确认流程。
- 对已有 `[x]` 或 `[X]` 任务检查相关代码与现有验证依据，避免重复实施；与现状明显不符或必须返工时说明原因并重新打开。无需无关全量重测。

### 2. 确定依赖与执行顺序

在满足前置依赖的条件下按清单顺序实施。共用前置任务先完成，影响同一文件的任务顺序处理。即使只有一个任务，也执行完整实现与验证流程。

已有明确优先级在依赖允许时沿用，不自行缩小为 MVP，不在完成第一个任务后停止。清单遗漏需求范围内必要步骤时，将步骤补入所属任务；确需新增独立任务时保留现有编号，使用高于已知最高编号的新编号并说明依据，不将范围外工作加入清单。

### 3. 逐任务实现并验证

对每个可执行任务：

1. 确认前置任务已满足完成标准，读取本任务对应需求、设计章节和相关实现。
2. 按目标与范围修改代码、配置和必要测试。沿用既有语言、版本、接口包装、状态编码、事务、权限和错误处理约定，覆盖需求中的正常流程、异常边界和兼容行为。
3. 保持既有风格和顺序，不引入无关结构调整。新增或修改方法添加方法注释，关键业务逻辑添加简洁注释；Java 实体与 DTO 每个字段采用 `/** 注释 */` 格式。
4. 不在 Controller 主动抽取公共方法；非 Controller 仅在本次新增或修改的重复代码超过 50 行、至少 3 处使用且用户未禁止时允许抽取。每个涉及的 Controller 接口入口记录 `[模块] 功能点 关键参数` 日志；关键业务节点记录业务标识、状态及结果，长链路按需增加阶段日志，避免密码、Token 等敏感数据。
5. 执行任务完成标准对应的必要验证，优先相关测试和项目规定检查。新增测试验证实际行为与关键风险，不为低影响可逆变更编写镜像实现的测试。明确要求 TDD 时按测试先行处理。
6. 验证失败时定位原因并修复，再运行受影响检查。通过后不无目的反复扩大验证；最后仍完成项目要求的整体检查和跨任务验收。
7. 只有实现与完成标准均满足后才将任务总览对应检查框改为 `[x]`，记录实际改动与验证依据，简要报告进度并继续下一任务。不将仅写完代码、未执行验证或仅编译成功当作全部完成标准满足。

### 4. 处理失败与中断

可自行解决的代码、配置和测试问题持续修复，不把首次失败直接交给用户。不得跳过失败检查、降低断言或修改需求来制造通过。

遇到缺少授权、必要环境或不可自行决定的业务问题时记录具体阻塞及影响任务；停止依赖该结果的任务，继续不受影响且前置满足的任务。不执行未满足依赖的任务，不把失败或受阻任务勾选完成。

中断后继续时读取现有清单、实现记录与工作区，从首个可执行未完成任务恢复，复用有效验证结果；相关代码或条件变化时重验。失败尝试的无效改动可以定向修正，不撤销用户已有工作。

### 5. 最终验收与记录

全部任务实施后核对需求场景、设计与实际代码，确认接口、字段、状态、权限、异常及事务行为一致；跨任务场景执行组合后的验收检查。运行项目强制的测试、格式、类型和构建检查，遵守用户已确定的验证范围。

检查最终差异、任务编号与真实状态，清理本轮占位与临时产物，不删除用户文件。不把任务均已勾选作为唯一完成依据；最终检查发现问题时修复并重新验证，必要时重新打开相关任务。

在《实现记录.md》中写清需求编号、来源、各任务真实状态、代码位置、实际验证命令或方式及结果、未完成项与阻塞。明确区分“通过”“失败”“未执行”，不编造测试覆盖率、运行结果或业务验收结论。不另建重复测试报告，详细日志仅在排查需要时引用。

## 完成与交付

只有授权范围内全部任务均实现、完成标准满足且必要检查通过，才宣称实施完成。存在任何受阻或未完成任务时明确报告部分完成，列出任务编号、原因和所需输入，不宣称全部完成。

交付实现记录与任务清单链接，说明完成任务数量、主要改动、验证结果及剩余限制。保持任务状态与代码、记录一致，不自动推进未经授权的发布操作。
