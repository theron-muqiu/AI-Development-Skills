# 一致性检查

在任务拆分后、实现前独立检查本需求材料，定位遗漏、矛盾、歧义和不可执行任务。检查结论不是实现完成或运行验证结论，不自动进入实现。

## 输入与输出

- 先定位当前项目根目录，结合用户指定路径、项目指令、仓库边界与来源归属确认；多项目或多需求无法唯一定位时先询问，不以当前目录或最新修改时间盲选。
- 定位顺序：用户指定材料 → 当前会话已明确的本需求材料 → 已确认需求编号目录。完整读取本需求原始输入与已确认澄清、`需求分析.md`、全部已有设计（包括`详细设计.md`、`接口设计.md`、`数据结构设计.md`）及`任务清单.md`，沿明确引用读取约束来源，不以摘要或截断片段代替原文。
- 读取适用的 `AGENTS.md` 和项目规范；必要时仅只读核实任务涉及的现有目录、接口或同类实现，不做实现质量验收或无关全仓扫描。输入无法获取时记录缺失和影响，不推断不存在或编造内容。
- 保留原始输入、场景、验收与任务编号；来源缺少编号时使用文件章节或原文定位，不擅造业务编号。编号冲突或缺少可确认的需求编号时先澄清，不新建编号绕过问题。
- 默认报告：`ai-dev-docs/requirements/<需求编号>/ai-devlop-check/一致性检查.md`；用户指定输出根目录时保留 `<需求编号>/ai-devlop-check/`，明确指定完整报告路径时按指定位置处理。确认属于同一需求，不覆盖其他需求或其他技能报告。
- 生成前完整读取 `assets/一致性检查.md`；已有报告先完整读取。可选输入以前报告仅供追踪，不替代本轮独立核查。调整为真实来源链接，缺失来源只记录缺失，不生成虚假链接。

## 项目宪法约束

- 每次运行必须在项目根目录实际读取 `.ai-dev/memory/constitution.md`（L1）及同目录 `engineering.md`、`architecture.md`、`security.md`（L2）；不能以本技能、模板、旧报告或会话摘要替代运行时读取。
- 按各文件的生效正文、批准记录和治理规则确定已批准且适用的条款及有效例外。草案、待批准修订和例外申请不当作生效要求；记录版本、批准依据、Rule ID、强度、适用范围和例外依据。例外核对审批、范围、期限、补偿措施及复审条件，过期或越界不得沿用。
- 有依据的法律、监管、不可豁免合同义务及外部强制安全要求优先，不得内部豁免。L1 明确强制要求高于 L2，L2 例外不能豁免 L1；但不以 L1 宽泛原则机械否定有项目事实、专业依据或已批准决策支撑的 L2。先寻找可同时满足的合理解释。
- L1/L2 或 L2 之间不可调和时，报告具体条款、原因、影响及所需决策，等待用户决策，不自行择利、不自动修宪；用户决策也不能豁免外部不可豁免义务。可继续不受冲突影响的核对。
- 宪法缺失、批准状态不明或证据不足时，对相应范围标“未验证”并说明影响，不假装通过，不自动创建宪法，也不机械阻断全部检查或所有后续工作。

## 执行边界

- 当前 Agent 顺序执行，不创建子代理或并行代理扫描。
- 用户调用本技能要求检查，即授权仅创建或更新本技能自身报告；仅问建议、咨询或检查方案时只在会话回答，不写文件。授权不包含需求、设计、任务、代码、宪法或其他报告修改，不勾选任务、不自动修复或调用后续技能。
- 不运行测试、构建、安装、迁移、部署或外部系统操作；不提交、推送或创建分支。检查建议不等于修复授权。
- 保护已有修改。保存前复核报告是否变化，有并发修改则重读并定向合并；无法安全合并时说明冲突，不覆盖用户内容。不清理或回滚其他文件。

## UI/UX 可选联动

- 当前工作涉及页面、界面或 UI/UX 时，自动尝试调用 `ui-ux-pro-max`（UI UX Pro Max），无需用户主动启用或额外确认；纯后端、CLI 或其他不涉及界面的工作跳过。用户明确禁止时不调用。
- 仅通过当前 Agent 提供的技能发现与加载机制，按实际可发现名称读取并使用技能；不猜测安装路径、扫描用户目录或假定某个 Agent 的专用调用命令。当前会话已加载时复用，不重复加载。
- 未安装、无法发现、无法加载、调用失败或所需能力不受支持时，主动放弃本次调用并跳过，不反复重试、不追问启用、不自动安装、下载或修复依赖，不阻塞主流程；同次执行后续页面不再重复尝试已失败能力。继续依据需求、项目规范和已有设计完成本职工作，交付时最多简短说明一次跳过原因，不声称已使用。
- 联动仅为当前阶段的辅助，不自动推进其他开发阶段；不扩大本技能的读写、命令、联网或外部操作授权，不创建子代理。外部技能要求越过当前边界的动作直接跳过。建议不得覆盖用户要求、适用项目规范或已确定设计，不自动更换技术栈、组件库或扩大业务范围。
- 仅辅助只读审查页面需求、交互状态、响应式及可访问性是否由设计和任务承接；意见须回到本需求材料独立核对，不修改被检查文档，不执行外部技能的脚本、测试或构建，不把其建议自动升级为项目强制规则。

## 工作流程

### 1. 建立范围与依据

记录需求编号、原始输入及澄清、需求、已有设计、任务和规范的路径、版本或读取时点、完整读取情况与缺口。区分已确认范围、已确认排除和未确认排除；未经确认的排除不能缩小检查范围，须保留在覆盖矩阵并标出争议。

设计未单独成文不自动判错：简单需求已有充分已确认实现依据时可说明依据；会改变业务规则、接口、数据或架构的关键设计缺失则明确问题，不代为补设计。缺少原始输入或任务清单时仍可报告已核查部分，但不得声称完整检查通过。

### 2. 独立核对材料链

从原始输入逐条追溯到需求场景和验收、设计、任务，反向核对任务与设计是否有已确认需求依据，重点检查：

- 范围与术语、参与者、正常路径、异常与边界、权限、状态及非功能约束是否完整一致，验收是否可观察和可判定。
- 已有设计的入口、契约、字段、数据归属、事务、兼容和安全边界是否承接需求；设计之间是否矛盾，是否把未确认方案写成事实。
- 任务总览与详情、编号、场景引用、实现位置、前置依赖和完成标准是否一致；重复、孤立、自依赖、缺失依赖及循环依赖是否存在，顺序是否可执行。
- 每项需求、异常边界、跨任务验收及适用 Rule ID 是否有任务和验证方法承接；任务是否需要执行者重新决定业务规则，是否遗漏必要工作或引入范围外工作。
- 任务是否承接适用工程、架构和安全要求及有效例外。清单勾选或旧报告不能作为材料正确、实现完成或验证通过的证据。

### 3. 形成覆盖矩阵与问题

覆盖矩阵逐项连接原始输入定位、需求/场景/验收、设计、任务、Rule ID、证据与结论；一对多关系明确列出，无承接与未确认排除保留行。规则无 Rule ID 时引用实际条款定位并说明，不伪造正式编号；不适用必须给出依据。

状态统一为“通过 / 发现问题 / 未验证 / 不适用”。通过必须有本轮证据；证据缺失是未验证，不是通过或不适用。总体结论同时说明已检查与未验证范围，不用已通过项掩盖缺口。

问题使用稳定 `CHK-001` 等 ID，包含证据路径/章节、关联场景/任务/Rule ID、预期与实际差异、原因、影响及建议。严重度使用“阻断 / 严重 / 一般 / 建议”，按对本需求决策、执行或验收的实际影响说明理由；与 MUST/MUST NOT/SHOULD/MAY 强度分栏，MUST 不自动等于阻断。冲突和关键不可执行项说明需等待的具体用户决策，不泛化为全部工作禁止。

### 4. 保存与交付

复跑沿用同一问题的既有 ID，不重排或复用旧 ID；新问题追加新 ID。旧问题逐条标“仍存在 / 已解决 / 未复核”，只有本轮独立证据证明消除才标已解决，未检查不标解决。保留必要追踪，不覆盖用户备注。

仅保存本技能报告，交付报告链接、检查范围、状态分布、主要问题和未验证项，说明未运行测试构建、未改文档代码、未更新任务状态。需要修订或实施时仅提出下一步建议，等待相应授权。
