# 技术设计

将明确的需求场景转化为可实施的设计，保持“需求场景 → 实现入口 → 接口及数据结构 → 场景实现设计”的对应关系。

## 输入与输出

- 必要输入：本次需求的《需求分析.md》、已确认补充说明和适用的项目规范。用户提供等价需求文档时检查是否具有可引用的稳定场景编号。
- 定位顺序：用户指定文件 → 当前会话明确生成或修订的需求 → 已明确功能目录中的需求。存在多个候选时询问目标，不按修改时间盲选。
- 缺少需求时说明需要的输入；缺少场景编号时先请用户授权通过 `$ai-devlop-spec` 补齐，不在设计中另造编号或擅改需求。
- 默认在需求文档同目录生成《详细设计.md》《接口设计.md》《数据结构设计.md》；用户指定输出目录时优先使用，并调整相对引用。
- 完整读取本技能 `assets/` 中同名的三份模板。模板是结构与示例，不是当前项目事实。
- 现有文档先读取再定向修改。用户只要求其中某份时，只更新指定产物，指出受影响但未授权修改的文档。

## 执行边界

- 当前 Agent 顺序完成，不创建研究代理或并行扫描代理。
- 遵守用户指令和适用的 `AGENTS.md`，从需求涉及的模块开始查找，避免无目的全仓库扫描。
- 本技能只进行设计与文档核对，不编写业务代码、运行迁移、部署、提交、创建分支或修改外部系统。
- 不自动增加 `research.md`、任务清单、测试报告或质量清单；关键技术决策按需写入现有设计章节。
- 不增加实施状态、实际验证结果或证据字段。设计中的“验证方式”描述将如何验证，不能宣称已经执行。
- 用户只要求分析或建议时，在会话中交付，不把技能触发当作写文件授权。

## 工作流程

### 1. 检查需求是否可设计

读取需求目标、范围、全局规则、场景编号与名称、处理步骤、异常边界、验收标准和业务状态。

检查是否存在编号重复、核心流程缺失、规则冲突、权限不明确或关键结果未确定。

- 已确认信息不重复提问。普通技术实现选择在项目规范范围内自行确定。
- 影响业务语义或范围的缺口，说明影响并提出聚焦问题，不以“技术设计”名义替用户决定。
- 若澄清会改变需求正文，先说明受影响内容，并在用户授权修订需求后保持两端一致；否则保留原文件并报告前置条件未满足。
- 可以继续与缺口无关的只读研究，但不把不确定设计当成最终产物，也不覆盖已有有效设计。

### 2. 检查相关项目现状

先读取直接相关的项目规范、构建配置、同类接口、业务类和数据定义，提取：

- 现有语言与框架版本、模块路径、分层习惯及可复用能力。
- 认证与数据权限、请求响应结构、状态值、时间格式和错误码。
- 字段类型、ID 生成方式、索引、事务、缓存和消息使用约定。
- 方法抽取限制、入口及业务节点日志要求，以及其他适用项目规则。

区分已查证的现状、用户给定约束和本次拟新增设计。没有源代码时不能编造已有类或表：按已确定的技术条件提出新设计，并标为“拟新增”。

新项目技术约束不足且会明显改变方案时，提出有取舍说明的建议并澄清。已有项目不因为模板采用 Java/MySQL 就替换真实技术栈；沿用模板的职责和表格，按实际技术调整名称。

### 3. 解决必要的技术问题

只研究会影响本次方案的未知项，优先使用现有实现、项目文档和对应版本的官方资料。

把重要选择、理由及必要的替代方案写入“设计概述”或相关场景。常规实现无需单独撰写选型报告。

发现方案违反项目强制规则时先调整方案；确需改变约束时向用户说明，不静默绕过。不自动发明性能指标或引入没有业务依据的中间件。

### 4. 编写接口设计

按 `assets/接口设计.md` 生成：

- 接口列表与详情的方法、路径、名称对应一致；每个实际接口都有完整详情，不能照搬模板只写两个示例。
- 参数位置、类型、必填、约束与默认值明确；路径参数必须出现在路径中。
- 返回字段与示例一致，沿用已有包装、状态、时间格式和错误码。
- 按需说明权限范围、重复请求行为；列表接口涉及分页排序时写清对应约定。
- 只设计需求实际需要的接口，不为了补齐 CRUD 增加功能。

对 CLI、库或消息入口按实际契约调整模板，不虚构 HTTP 入口。若本次没有新增或变更的对外契约，文件简要说明“不涉及”及原因，删除虚构示例。

### 5. 编写数据结构设计

按 `assets/数据结构设计.md` 生成：

- 关系图与字段、实体名称一致；说明逻辑关联是否落实为数据库外键，不能从图中臆推物理外键。
- 使用关系数据库时给出真实或拟新增的字段类型、可空、默认值和主键／唯一／普通索引；联合索引字段顺序及用途明确，必要的约束写入说明。
- 区分“无默认值”和 `NULL`；ID 生成及业务枚举按项目现有约定说明。
- Redis、MQ 和其他结构仅在实际涉及时保留；字段结构在本文件维护，更新时机与失败策略由详细设计承接。
- 修改存量结构时按需说明旧数据、兼容及迁移影响，不执行迁移。

本次不涉及持久化、缓存或消息结构时仍交付该文件，简要说明“不涉及”及原因，不创造示例表来填满模板。

### 6. 编写详细设计并连接三份产物

按 `assets/详细设计.md` 生成：

- **需求场景对应表**：沿用每个需求场景的编号与名称，列出实现入口、关联接口、关联数据结构和设计位置。支持一对多，接口和数据使用具体章节引用；无关联写“不涉及”。
- 不在本次实现范围的场景仍列出，并注明已确认的范围依据；未确认的排除不能自行填写。
- **模块设计**：说明类／方法职责、参数返回及共用方法行为。只有单场景使用的业务步骤集中写在场景章节。
- **场景实现设计**：逐编号描述调用顺序、业务判断、状态变化、异常边界和验收对应；共用行为引用模块设计，并说明调用条件。
- **事务、并发与异常**：集中描述实际涉及的共用策略，场景引用并说明使用位置。标明事务范围、提交条件、回滚条件及范围；事务外操作按需说明时机、失败后的状态和处理方式。
- **代码变更**：列出拟新增／修改／删除的位置及目的，使用已核对的路径或明确的拟新增路径，不写成代码已完成。

数据库回滚不能自动撤销 Redis、MQ 或外部调用的副作用。重试、补偿、锁与幂等机制按实际需求选择，不全部堆入方案。

同一逻辑只在一处完整描述，其他章节引用。共用方法指已有或已确定的方法，不为文档结构进行额外抽取。遵守 Controller 不主动抽取、非 Controller 仅在项目允许条件下抽取的约束；按项目要求在处理步骤中标明入口及关键节点日志，避免敏感信息。

### 7. 交叉核对并修正

直接在本轮核对，不新增检查报告文件：

1. 需求场景列表与设计对应表的编号集合、名称一致；在范围内的每个场景均有实现设计。
2. 每个场景的正常规则、异常边界、状态变化及验收标准都有对应实现方式；只出现编号不等于覆盖完整。
3. 关联接口在接口文档中确实存在，关联数据结构在数据文档中存在；引用可以定位到具体章节。
4. 接口字段、数据字段、枚举、权限、幂等和错误行为一致。展示格式与存储类型不同需要解释转换。
5. 类／方法引用一致；拟新增内容有明确标识，已有实现有实际依据。
6. 事务、并发及失败策略符合业务要求和项目约束，没有重复或矛盾的描述。
7. 文档中没有未替换占位符、待确认问题或未选定候选方案；相对链接、标题、表格和代码围栏正确。
8. 未加入实施状态、验证结果、证据字段，未把设计核对声称为实际测试。

可依据已确认事实修正的问题直接修正；需要业务决定的问题回到澄清，不以猜测完成文档。

## 交付

用户没有要求实施时，到设计结束，不自动拆任务或开始编码。
