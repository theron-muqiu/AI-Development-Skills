# 旧 Markdown 需求迁移到 JSON

旧需求继续用原 Markdown 维护。需要迁移某个需求时，先确认同一需求编号和完整材料，再逐份建立七类 JSON；不得把整个 Markdown 正文塞进单个 JSON 字符串。迁移完成前不切换维护源，旧文件留作历史。

## 转换顺序

1. 将所有用户原始输入按真实时间正序放入 `原始需求/原始需求.json`；保留原文、时间来源、问题上下文和附件路径。旧文档没有原始记录时注明缺失，不从总结反推用户原话。
2. 将需求的术语、范围、规则、场景、步骤、异常、验收与状态变化分拆为对应实体。保留 `S-001` 等稳定编号，每项结论补可定位的 `sourceRefs`；找不到出处时先澄清。
3. 将三份设计中的接口、字段、索引、模块、事务、并发和场景对应分别写入 JSON，跨文档用相对路径加实体 ID。保留现有接口和状态约定，不照搬示例值。
4. 将任务清单的每个 `T001` 等任务转换为独立实体，保留依赖、完成标准及真实当前状态。原 `[x]` 只有在代码与验证依据仍有效时才转为 `completed`。
5. 将实现记录中的实际命令、结果和修改位置作为历史事实录入。若旧文档没有验证证据，不能推断 `passed`。澄清导致返工时重开任务并保留旧验证记录。
6. 运行 `ai-devlop docs validate <需求目录>`，逐项比对旧文档与 JSON 的场景、出处、字段、状态和验收，随后运行 `ai-devlop docs render <需求目录>`。校验及人工核对通过后以 JSON 为唯一维护源。

## 对照示例

旧文档中的内容：

```md
### S-001 取消未发货订单
1. 用户提交取消请求。
2. 未发货订单取消成功；已发货订单返回不可取消。

验收：未发货订单提交后状态变为已取消。
```

对应 JSON 中的场景与验收可按 `skills/ai-devlop-spec/assets/需求分析.json` 的结构拆分，例如：

```json
{
  "id": "S-001",
  "name": "取消未发货订单",
  "summary": "用户取消未发货订单。",
  "steps": [{"id": "STEP-001", "text": "用户提交取消请求。", "sourceRefs": [{"path": "../原始需求/原始需求.json", "id": "I-001"}]}],
  "exceptions": [{"id": "EX-001", "condition": "订单已发货", "result": "返回不可取消。", "sourceRefs": [{"path": "../原始需求/原始需求.json", "id": "I-001"}]}],
  "acceptance": [{"id": "A-001", "precondition": "订单未发货", "action": "提交取消请求", "expected": "订单状态变为已取消", "sourceRefs": [{"path": "../原始需求/原始需求.json", "id": "I-001"}]}],
  "sourceRefs": [{"path": "../原始需求/原始需求.json", "id": "I-001"}]
}
```

此示例只是字段映射；真实迁移必须核对原始材料是否支持每一条出处。仓库 `tests/fixtures/valid-requirement/` 提供七类 JSON 的贯穿样例，可用 CLI 校验与生成 HTML 检查展示结果。
